# Manually authoring workflows

This guide is the complete V1 path for authors who want to write workflow packages directly
instead of using the conversational creator. It covers package creation, every supported package
file, manifest fields, input and output types, all six step types, offline tests, revision safety,
and source-control sharing.

Manual packages use the same parser, validator, permission checks, execution hashes, runner, and
journal as generated packages. Existing packages can also use a host-managed manual revision
lifecycle with an isolated draft, deterministic validation and tests, semantic and authority
diffs, stale-base protection, revision incrementing, archival, and adapter regeneration.

Commands in this guide beginning with `cleetus workflow` are standalone shell commands. The
interactive TUI additionally supports the complete managed revision loop with `/workflow edit`,
`/workflow review`, `/workflow publish`, and `/workflow discard`. Inside an interactive session,
`/workflow review` and `/workflow discard` without a workflow name continue to operate on
conversational creator drafts.

## Create a valid skeleton

Command syntax: `cleetus workflow init <name> [--global] [--description <text>]`.

From the project where the workflow should be available:

```bash
cleetus workflow init repository-brief
```

The default project path is:

```text
<project>/.cleetus/workflows/repository-brief/
```

Create a global workflow instead:

```bash
cleetus workflow init repository-brief --global
```

Set the initial description without editing it afterward:

```bash
cleetus workflow init repository-brief \
  --description "Fetch repository metadata and render a concise brief"
```

`init` requires a lowercase, hyphen-separated name, never overwrites an existing directory, and
creates a package that already validates and has a passing offline test. It does not call a model.
The skeleton is discoverable immediately, but execution still requires the normal exact-revision
permission decision.

The generated step only renders placeholder Markdown. Replace it rather than treating the
skeleton as useful behavior.

## Package layout

```text
repository-brief/
  workflow.yaml
  SKILL.md
  prompts/
  scripts/
  tests/
    skeleton.yaml
```

| Path | Runtime role | Required |
| --- | --- | --- |
| `workflow.yaml` | Executable definition: identity, interfaces, permissions, steps, outputs, and presentation. | Yes |
| `SKILL.md` | Deterministic discovery adapter telling the agent to invoke the named workflow. It never defines execution. | Recommended; generated by `init` and regenerated by `publish` |
| `prompts/` | UTF-8 prompt files referenced by `llm.generate@1` as `./prompts/<file>`. | Only when referenced |
| `scripts/` | Packaged scripts referenced by `command.run@1` arguments as `./scripts/<file>`. | Only when referenced |
| `tests/*.yaml` or `tests/*.json` | Offline mock cases. External HTTP, model, and command steps never execute during these tests. | Strongly recommended |

Other regular files are allowed and affect the package hash. Only referenced prompt and script
resources affect the execution hash. Symlinks are rejected anywhere in the package. The directory
name must exactly match `workflow.yaml`'s `name`.

Empty `prompts/` and `scripts/` directories are created as authoring affordances. Delete them if
the workflow does not use them.

### `SKILL.md`

`SKILL.md` makes the workflow visible to the skill-discovery layer, but `/skill` does not execute
it. `workflow.yaml` remains executable truth. `init` generates this form:

```markdown
---
name: repository-brief
description: Fetch repository metadata and render a concise brief
metadata:
  cleetus-workflow: workflow.yaml
---

Run the `repository-brief` Cleetus workflow when the user asks for this operation.
Use `/workflow run repository-brief`; do not reproduce its steps manually.
```

Do not spend time editing this generated adapter inside a managed revision. `workflow publish`
regenerates it from the manifest. A direct edit of the active package does not.

## The initial package authoring loop

`init` creates a new skeleton directly in the active registry. After each meaningful edit to that
initial package:

```bash
cleetus workflow validate repository-brief
cleetus workflow test repository-brief
cleetus workflow dry-run repository-brief --inputs-json examples/repository-input.json
```

Then perform the first real run interactively and choose **Allow once**. Inspect the output and
history before trusting the exact revision:

```text
/workflow run repository-brief
/workflow history repository-brief latest
```

Validation is structural and performs no HTTP, command, model, or filesystem work. Offline tests
run deterministic steps and replace every external step with declared data. Dry-run validates
real inputs and resolves everything available before execution without performing external work.
For later revisions, use the isolated `revise` and `review` lifecycle described below; `validate`,
`test`, and `dry-run` address only active packages by name.

## `workflow.yaml`

The manifest is strict YAML. Duplicate keys, unknown fields, malformed schemas, unsupported step
versions, invalid references, and undeclared authority fail validation.

```yaml
schema_version: 1
name: repository-brief
revision: 1
description: Fetch repository metadata and render a concise brief
inputs:
  type: object
  additionalProperties: false
  required: [owner, repository]
  properties:
    owner:
      type: string
      minLength: 1
    repository:
      type: string
      minLength: 1
permissions:
  network:
    - host: api.github.com
      methods: [GET]
execution:
  timeout: 1m
steps:
  - id: fetch
    uses: http.request@1
    with:
      url: https://api.github.com/repos/${inputs.owner}/${inputs.repository}
      response: json
  - id: render
    uses: text.template@1
    with:
      template: |
        # {{name}}

        {{description}}
      data:
        name: $steps.fetch.output.body.name
        description: $steps.fetch.output.body.description
outputs:
  markdown:
    value: $steps.render.output
    schema:
      type: string
presentation:
  output: markdown
```

### Top-level fields

| Field | Type | Required | Meaning |
| --- | --- | ---: | --- |
| `schema_version` | Integer `1` | Yes | V1 manifest grammar. |
| `name` | String | Yes | Lowercase letters and numbers separated by single hyphens; must match the directory. |
| `revision` | Positive integer | Yes | Human-readable package revision. Managed publish assigns the next value; increment it yourself only for direct active-package edits. |
| `description` | Nonempty string, at most 500 characters | Yes | User-facing purpose and adapter description. |
| `inputs` | JSON Schema object | Yes | Schema for the one input object. No type coercion occurs. |
| `secrets` | Object of secret declarations | No | Environment-backed values, separate from normal inputs. |
| `permissions` | Permission object | Yes | Maximum authority any step may use. `{}` means no external authority. |
| `execution` | Object | Yes | Workflow timeout and optional workflow-wide model selection. |
| `steps` | Nonempty ordered array | Yes | Linear, pinned executor calls. |
| `outputs` | Nonempty object | Yes | Named values, each with its own validation schema. |
| `presentation` | Object | No | Selects one declared output for normal Markdown/JSON display. |

Durations are positive integers followed by `ms`, `s`, or `m`, such as `500ms`, `30s`, or `2m`.

## Inputs and JSON types

The workflow receives exactly one JSON object. Supported JSON value types are:

| JSON Schema `type` | Runtime value | Typical constraints |
| --- | --- | --- |
| `string` | Text | `minLength`, `maxLength`, `pattern`, `enum`, `default` |
| `number` | Finite number | `minimum`, `maximum`, `enum`, `default` |
| `integer` | Whole finite number | `minimum`, `maximum`, `enum`, `default` |
| `boolean` | `true` or `false` | `default` |
| `null` | `null` | Usually used through a union |
| `array` | Ordered JSON values | `items`, `minItems`, `maxItems`, `default` |
| `object` | String-keyed JSON values | `properties`, `required`, `additionalProperties`, `default` |

Cleetus uses strict AJV validation with type coercion disabled. Remote `$ref` values are rejected.
Formats are not validated. Local schema composition supported by AJV can be used, but simple,
closed schemas are easier for static reference validation and interactive input collection.

Use `additionalProperties: false` unless intentionally accepting free-form fields. Required paths
referenced by a step must be declared in `required` or materialized by defaults. Defaults are
applied recursively before validation.

```yaml
inputs:
  type: object
  additionalProperties: false
  required: [question, options]
  properties:
    question:
      type: string
      minLength: 1
    options:
      type: array
      minItems: 2
      items:
        type: object
        additionalProperties: false
        required: [name, advantages, disadvantages]
        properties:
          name: { type: string, minLength: 1 }
          advantages:
            type: array
            items: { type: string }
          disadvantages:
            type: array
            items: { type: string }
    constraints:
      type: array
      items: { type: string }
      default: []
```

Secrets are not input fields and cannot be supplied through `--input` or `--inputs-json`.

## Values and references

Every `with` value and output value is JSON-compatible YAML: string, number, boolean, null, array,
or object.

Whole-value references preserve their JSON type:

```text
$inputs.<path>
$steps.<earlier-step-id>.output.<path>
$run.id
$run.started_at
$run.workspace
$secrets.<declared-name>
```

Examples:

```yaml
input: $steps.fetch.output.body
data:
  title: $inputs.title
  first_item: $steps.select.output.items.0
```

Scalar interpolation embeds strings, numbers, booleans, or null in a larger string:

```yaml
url: https://api.example.com/users/${inputs.username}
Authorization: "Bearer ${secrets.api-token}"
```

Objects and arrays cannot be interpolated into strings. References to steps must point backward;
there are no conditions, expressions, arithmetic, loops over steps, or forward references.

## Common step fields

```yaml
- id: fetch
  uses: http.request@1
  timeout: 30s
  retry:
    attempts: 2
    backoff:
      initial: 500ms
      multiplier: 2
      maximum: 5s
    when: [timeout, connection_error]
  allow_untrusted_input: false
  with: {}
```

| Field | Type | Required | Meaning |
| --- | --- | ---: | --- |
| `id` | Hyphen-separated name | Yes | Unique step identity used by later references and test mocks. |
| `uses` | Pinned executor string | Yes | One of the six `@1` step types below. |
| `timeout` | Duration | No | Overrides the executor's finite default. |
| `retry` | Retry policy | No | Bounded retries, accepted only for executor-supported error classes. |
| `allow_untrusted_input` | Boolean | No | Explicitly permits a command step whose resolved input contains any untrusted data. Avoid unless reviewed. |
| `with` | Object | Yes | Executor-specific input. Unknown fields fail validation. |

`attempts` is the number of retries after the first attempt, from 0 through 10. Supported retry
class names are `timeout`, `connection_error`, `http_429`, `http_5xx`, and `provider_error`.
Only HTTP and model steps allow the applicable subsets described below.

## Supported actions

### `http.request@1`

Makes one SSRF-checked, DNS-pinned HTTP request and follows at most five redirects. Default timeout:
30 seconds.

| `with` field | Type | Required | Default / notes |
| --- | --- | ---: | --- |
| `url` | String, at most 8,192 characters | Yes | Absolute request URL. |
| `method` | Alphabetic string | No | `GET`; normalized to uppercase. |
| `query` | Object | No | Each value is a string, number, boolean, or array of those scalar types. |
| `headers` | String-to-string object | No | At most 64 headers and 32 KiB; transport-controlled headers are rejected. |
| `body` | JSON value or string | No | Non-string JSON is serialized. |
| `expected_status` | Array of HTTP integers | No | `[200]`. |
| `expected_content_type` | String | No | Case-insensitive substring required in the response content type. |
| `response` | `json` or `text` | No | JSON is also inferred when the response content type contains `json`. |
| `max_response_bytes` | Integer 1–8,388,608 | No | 1,048,576 bytes. |
| `idempotency_key` | Nonempty string | No | Adds `Idempotency-Key` and classifies a mutating request as idempotent. |
| `allow_unsafe_retry` | Boolean | No | Allows retry classes for otherwise unsafe methods; use only with external idempotency. |

Output:

```yaml
status: 200          # integer
content_type: application/json
final_url: https://api.example.com/result
body: {}             # any JSON value, or text
```

GET and HEAD may retry `timeout`, `connection_error`, `http_429`, and `http_5xx`. Mutating methods
may retry those classes only with `idempotency_key` or `allow_unsafe_retry`.

Required permission:

```yaml
permissions:
  network:
    - host: api.example.com
      methods: [GET]
```

### `llm.generate@1`

Runs one fresh, tool-free, schema-constrained model transformation. It receives no conversation
history. Default timeout: two minutes.

| `with` field | Type | Required | Default / notes |
| --- | --- | ---: | --- |
| `prompt` | Nonempty string | Yes | Inline prompt or `./prompts/<file>`; maximum 1 MiB. |
| `input` | Any JSON value | Yes | Data supplied separately from the host-owned system boundary. |
| `output_schema` | JSON Schema object | Yes | The step output must validate against this schema. |
| `provider` | Nonempty string | No | Inherits workflow/run/default selection. |
| `model` | Nonempty string | No | Inherits workflow/run/default selection. |
| `max_output_tokens` | Integer 1–65,536 | No | Omit to inherit the provider/model budget. |
| `repair_attempts` | Integer 0–3 | No | `1`; bounded schema-repair model calls. |

Output: exactly the JSON value described by `output_schema`. It may be a string, number, boolean,
null, array, or object.

The step may retry `timeout` and `provider_error`. Schema repair attempts are separate model calls
inside one step attempt. `repair_attempts: 1` therefore permits up to two model calls for that
attempt.

Required permission:

```yaml
permissions:
  model: true
```

### `data.select@1`

Selects a value using RFC 6901 JSON Pointer. Default timeout: one second.

| `with` field | Type | Required | Default / notes |
| --- | --- | ---: | --- |
| `value` | Any JSON value | Yes | Usually a whole earlier step output. |
| `pointer` | String | Yes | `""` selects the whole value; otherwise begin with `/`. |
| `default` | Any JSON value | No | Returned when the pointer does not match; omission makes no-match fail. |

Output: the selected value or declared default, preserving its JSON type.

This action needs no permission and does not support retries.

### `text.template@1`

Renders deterministic, HTML-escaped text. Default timeout: one second.

| `with` field | Type | Required | Default / notes |
| --- | --- | ---: | --- |
| `template` | String, at most 100,000 characters | Yes | Inline template only. |
| `data` | Any JSON value | Yes | Values available to template paths. |

Output: string.

Supported template forms:

```handlebars
{{name}}
{{path.to.value}}
{{#each items}}- {{this}}
{{/each}}
{{#each actions}}- {{this.description}} — {{this.owner}}
{{/each}}
```

Interpolated values must be scalar. Raw interpolation, nested loops, arbitrary expressions, and
other directives are rejected. Escaping means apostrophes appear as `&#39;` in the raw step
output but render normally in the interactive Markdown view.

This action needs no permission and does not support retries.

### `assert.schema@1`

Validates a value and returns it unchanged. Default timeout: one second.

| `with` field | Type | Required |
| --- | --- | ---: |
| `value` | Any JSON value | Yes |
| `schema` | JSON Schema object | Yes |

Output: the original value, with the same JSON type, after successful validation.

This action needs no permission and does not support retries.

### `command.run@1`

Runs one exact program through the configured sandbox without invoking a shell. Default timeout:
one minute.

| `with` field | Type | Required | Default / notes |
| --- | --- | ---: | --- |
| `program` | Nonempty string | Yes | Executable name. |
| `args` | Array of strings, at most 1,000 | No | `[]`. |
| `stdin` | String, at most 8 MiB | No | No stdin. |
| `output` | `text` or `json` | Yes | Controls parsing of stdout. |
| `cwd` | Nonempty string | No | Workflow workspace; resolved cwd cannot escape it. |
| `env` | String-to-string object, at most 128 entries | No | Additional command environment. |
| `max_output_bytes` | Integer 1–8,388,608 | No | 1,048,576 bytes for each captured stream. |

Output:

```yaml
stdout: {}        # string for text mode; any parsed JSON value for json mode
stderr: ""        # string
exit_code: 0      # integer; nonzero exits fail the step
survivors: []     # array of process IDs reported by the sandbox
```

Packaged JavaScript and TypeScript must use:

```yaml
with:
  program: bun
  args: [run, ./scripts/task.ts]
  output: json
```

Required permission should constrain the exact static argument prefix:

```yaml
permissions:
  commands:
    - program: bun
      args_prefix: [run, ./scripts/task.ts]
```

HTTP and command output, plus ordinary workflow inputs, are marked untrusted. The current command
guard is intentionally coarse: if any resolved command input contains untrusted data, the step is
blocked unless it explicitly sets `allow_untrusted_input: true`. This is required even when the
untrusted value is intended only for `stdin`; review the static `program`, `args`, and `cwd` before
opting in. Command steps do not support retries.

## Permissions

The manifest declares maximum authority:

```yaml
permissions:
  network:
    - host: api.example.com
      methods: [GET]
  commands:
    - program: bun
      args_prefix: [run, ./scripts/report.ts]
  filesystem:
    read: [$project/data/**]
    write: [$project/reports/**]
  model: true
```

| Permission | Type | Meaning |
| --- | --- | --- |
| `network` | Array of `{host, methods}` | Exact hostname and HTTP-method envelope. Redirects are checked again. |
| `commands` | Array of `{program, args_prefix?}` | Exact program; optional argument prefix narrows authority. |
| `filesystem.read` | Array of paths | Read envelope, with `$project/` rooted at the run workspace. |
| `filesystem.write` | Array of paths | Write envelope, with `$project/` rooted at the run workspace. |
| `model` | Boolean | Whether any model generation is allowed. |

Validation rejects statically known step authority outside this envelope. The execution prompt and
persisted grant use the normalized capability set and exact execution hash.

## Secrets

V1 secrets come from environment variables:

```yaml
secrets:
  github-token:
    source: env
    name: CLEETUS_WORKFLOW_GITHUB_TOKEN
```

Use `$secrets.github-token` as a whole value or `${secrets.github-token}` inside a scalar string.
Missing required environment values fail before execution.

Model exposure is denied by default:

```yaml
secrets:
  private-context:
    source: env
    name: PRIVATE_CONTEXT
    expose_to_llm: [summarize]
```

`expose_to_llm` contains exact step IDs. Never place secret values in the manifest, prompts,
scripts, tests, normal outputs, or committed example input files.

## Outputs and presentation

Each output contains a value and its JSON Schema:

```yaml
outputs:
  structured:
    value: $steps.analyze.output
    schema:
      type: object
      additionalProperties: false
      required: [summary, risks]
      properties:
        summary: { type: string }
        risks:
          type: array
          items: { type: string }
  markdown:
    value: $steps.render.output
    schema: { type: string }

presentation:
  output: markdown
```

Output values may be any JSON type. All named outputs are resolved and schema-validated before a
run succeeds. `presentation.output` must name one declared output:

- String: sanitized Markdown.
- Nonempty array containing only strings: Markdown bullets.
- Other JSON values: formatted JSON.
- `--json`: always returns the complete result envelope.

## Offline test files

Tests are YAML or JSON objects:

```yaml
schema_version: 1
name: renders repository brief
mode: mock
inputs:
  owner: oven-sh
  repository: bun
mocks:
  fetch:
    output:
      status: 200
      content_type: application/json
      final_url: https://api.github.com/repos/oven-sh/bun
      body:
        name: bun
        description: JavaScript runtime and toolkit
expect:
  status: succeeded
  outputs:
    markdown: |
      # bun

      JavaScript runtime and toolkit
  attempts:
    fetch: 1
    render: 1
```

| Field | Type | Required | Meaning |
| --- | --- | ---: | --- |
| `schema_version` | Integer `1` | Yes | Test grammar version. |
| `name` | Nonempty string | Yes | Display name. |
| `mode` | `mock` | No | Only mock mode exists; live tests are rejected. |
| `inputs` | Object | No | Defaults to `{}`; normal workflow defaults and validation apply. |
| `mocks` | Object keyed by step ID | Yes | Each value contains exactly one of `output` or `error`. |
| `expect.status` | `succeeded`, `failed`, or `cancelled` | Yes | Expected final status. |
| `expect.outputs` | Object | No | Exact named-output comparison. |
| `expect.failed_step` | Step ID string | No | Expected failed step. |
| `expect.attempts` | Integer object keyed by step ID | No | Exact attempt counts. |

Every `http.request@1`, `llm.generate@1`, and `command.run@1` step needs a mock. Deterministic steps
execute normally.

- HTTP mock output uses the complete `{status, content_type, final_url, body}` envelope.
- Model mock output is the model step's structured value itself.
- Command mock output uses `{stdout, stderr, exit_code, survivors}`; `stdout` matches text or JSON
  mode.
- Error mocks use `{error: {message, class}}`.

Tests compare outputs exactly, including Markdown whitespace. They never read real secrets; declared
secrets resolve to synthetic sensitive placeholders.

## Manual revisions and trust

Editing an active package changes what the registry sees on its next command. A changed
`workflow.yaml`, referenced prompt, or referenced script changes the execution hash, so an old
trusted grant does not authorize the new behavior.

From an interactive Cleetus session, prefer:

```text
/workflow edit repository-brief
```

This creates or reopens a hidden, non-discoverable draft, records the immutable base revision and
hashes, hands the terminal to `$EDITOR`, and automatically reviews the draft when the editor exits.
The active package remains runnable and cannot observe a partially edited draft. See
[Editing files from Cleetus](../editor.md).

The equivalent split shell workflow begins with `cleetus workflow revise repository-brief`.

Review the draft:

```text
/workflow review repository-brief
```

Review performs no live workflow execution. It:

- validates the draft against the step registry built for that package;
- runs all packaged mock tests;
- detects whether the active package changed after revision authoring began;
- shows manifest, resource, test, authority, and deterministic risk changes;
- reports whether publishing is currently allowed.

When the review is clean, publish locally:

```text
/workflow publish repository-brief
```

`publish` repeats validation, tests, and the stale-base check. It then assigns the next numeric
revision, regenerates `SKILL.md`, archives the previous active package under `.revisions/`, and
atomically activates the edited package. Publishing never runs the workflow.

The draft's `revision` and `SKILL.md` are managed outputs. Leave the copied revision number in
place; publish assigns the next one. Any draft edit to `SKILL.md` is discarded when the adapter is
regenerated.

Discard an unwanted draft without changing the active package:

```text
/workflow discard repository-brief
```

The standalone `cleetus workflow review`, `publish`, and `discard` forms remain available for
scripts and separate terminals. Add `--global` to all lifecycle commands when explicitly targeting
a global workflow. Without it,
`revise` follows normal project-over-global resolution. `review`, `publish`, and `discard` use the
project draft when one exists, otherwise the global draft.

Only one manual draft per workflow and scope is allowed. If the active package changes after
`revise`, publishing is blocked rather than silently rebasing the work. `workflow discard` removes
only the isolated draft; it never restores or changes the active package. If the active edits are
intentional, discard the stale draft, start a new revision against the current active package, and
reapply any draft-only work. If the active edits are accidental, first restore the active files
from source control or another known-good copy, then discard or restart the draft as appropriate.
Cleetus does not currently provide an active-package restore command.

Directly editing an active package remains possible, but it does not preserve a base, archive the
old package, increment the revision, regenerate the adapter, or protect readers from an invalid
intermediate state. Use direct editing only when that reduced lifecycle is intentional.

## Sharing and publishing

V1 has no remote workflow registry. `workflow publish` means local atomic activation of one manual
revision; it does not upload or distribute a package.

For local activation, “published” means the valid package directory exists under the project or
global workflows root. `init` creates a new skeleton there immediately; `publish` replaces an
existing package after managed review.

For team sharing, commit the project package to source control. Many repositories ignore all of
`.cleetus/`; if so, add narrow exceptions and keep runtime state ignored:

```gitignore
.cleetus/*
!.cleetus/workflows/
!.cleetus/workflows/**
.cleetus/workflows/.drafts/
.cleetus/workflows/.manual-drafts/
.cleetus/workflows/.revisions/
```

Review the repository's existing ignore rules before changing them. Never commit:

- `.cleetus/workflows.db`;
- `.cleetus/workflow-grants.yaml`;
- `.cleetus/workflows/.drafts/`;
- `.cleetus/workflows/.manual-drafts/`;
- `.cleetus/workflows/.revisions/`;
- environment files or secret values.

Global workflows live outside the project and are not automatically publishable. Copy a reviewed
package into a repository-owned project workflow when it should be shared.

## Completion checklist

- Directory and manifest names match.
- Description is current; managed publish assigns the next revision.
- Inputs are closed and required/defaulted paths cannot be missing.
- Every reference points to inputs, run metadata, a declared secret, or an earlier step.
- Every step uses one supported pinned `@1` executor.
- Permissions cover the exact maximum authority without unnecessary breadth.
- Secrets are environment declarations and model exposure is explicit.
- Outputs have schemas and presentation names a declared output.
- Every external step has at least one offline mock.
- Managed `review` passes; use `dry-run` against the published package with representative inputs.
- The first live run uses **Allow once** and its detailed history is inspected.

For parser-level detail and runtime limits, see the
[workflow manifest and runtime reference](reference.md). For failure messages, see
[workflow troubleshooting](troubleshooting.md).
